1. THE CORE PROBLEM & MISSION
--------------------------------------------------------------------------------
In modern software delivery, automated CI/CD pipelines often push code directly
to production without validating runtime security. When security scanning is
performed, results typically arrive as unmanageable 100+ page XML/JSON reports
that release managers cannot parse and developers frequently ignore.

SecureGate acts as a deterministic Pre-Release Security Gate. It sits between
dynamic application security scanning (OWASP ZAP) and production release
promotion.

SecureGate's mandate:
  1. Ingest raw DAST scan reports directly from OWASP ZAP.
  2. Normalize findings to industry standards (OWASP Top 10 2021 & CWE).
  3. Enforce an automated, deterministic release gate policy:
       - CRITICAL      --> BLOCK
       - HIGH          --> BLOCK
       - MEDIUM        --> REVIEW (Manual security sign-off required)
       - LOW           --> PASS
       - INFORMATIONAL --> PASS
  4. Compute an explainable, secondary Security Posture Score (0 - 100).
  5. Provide developers with immediate evidence, attack parameters, and
     remediation blueprints.

3. DATA NORMALIZATION & POLICY ENGINE
--------------------------------------------------------------------------------

A. DAST Scanner Ingestion (backend/app/parsers/zap_parser.py):
   ZAP reports alerts with a numerical 'riskcode':
     - riskcode "4" --> Critical
     - riskcode "3" --> High
     - riskcode "2" --> Medium
     - riskcode "1" --> Low
     - riskcode "0" --> Informational

   * CRITICAL FIX IMPLEMENTED:
     Informational findings (riskcode 0) are NEVER converted to Low findings.
     They are strictly preserved as Informational across all counters,
     breakdown bars, metrics, and report exports.

B. Deterministic Gate Evaluation (backend/app/security/severity_engine.py):
   The release gate policy is applied deterministically:
     - If count(Critical) > 0 OR count(High) > 0:
         STATUS = "BLOCK"
         REASON = "Release blocked due to: X Critical, Y High. Critical/High
                   findings violate the release policy."
     - Else if count(Medium) > 0:
         STATUS = "REVIEW"
         REASON = "Release requires review due to: X Medium. Medium severity
                   findings require security sign-off."
     - Else:
         STATUS = "PASS"
         REASON = "Release passed. No High or Critical vulnerabilities were
                   detected. The release can proceed."

C. Secondary Security Score Engine:
   The security score is explainable and deterministic:
     Base score: 100 points
     - Critical Finding:      -40 points per finding
     - High Finding:          -25 points per finding
     - Medium Finding:        -10 points per finding
     - Low Finding:           -3 points per finding
     - Informational Finding:  0 points (Zero deduction)
     Bounded between 0 and 100.

   IMPORTANT: The security score is strictly SECONDARY. A scan scoring 85/100
   that contains even one High finding is still unconditionally BLOCKED.

4. SINGLE AUTHORITATIVE ACTIVE SCAN MODEL
--------------------------------------------------------------------------------
In earlier builds, a data inconsistency existed where the dashboard could show
PASS while the AI widget claimed multiple High findings existed.

This has been completely solved:
  - The entire application (Dashboard, Findings, Releases, Reports, and the
    Security Analysis Assistant) derives from a SINGLE active scan context
    (active_scan_id).
  - When you import a scan, click a preset, or click "Set as Active" in the
    Scans page, that scan ID becomes the universal context.
  - The Assistant inspects the active scan object in real-time and computes its
    summary from live severity counts and gate determinations. No hardcoded
    assumptions exist anywhere.

6. KEY UI & USER EXPERIENCE FEATURES
--------------------------------------------------------------------------------

A. Hero Banner ("PRE-RELEASE SECURITY GATE"):
   - Displays massive, bold status text: PASS / BLOCK / REVIEW.
   - Shows severity pill badges with exact counts.
   - States the exact gating reason and next recommended action.
   - Includes quick-action buttons to view findings or release history.

B. Release Gate Policy Card:
   - Compact table displayed directly on the dashboard:
       Critical      --> BLOCK
       High          --> BLOCK
       Medium        --> REVIEW
       Low           --> PASS
       Informational --> PASS
   - Explicit rule: "Release is blocked if any Critical or High severity
     vulnerability is detected."

C. Five Distinct Severity Metrics:
   - 6 responsive cards across the top:
       [Critical] [High] [Medium] [Low] [Informational] [Security Score]
   - Each card lists counts and threshold expectations.

D. Finding Detail Modal (Deep Inspector):
   - Header with severity badge, confidence rating, CWE, and OWASP category.
   - Bold Gate Impact banner (e.g., "Gate impact: BLOCK — High severity
     finding violates release gate policy").
   - HTTP method and vulnerable endpoint URL.
   - Raw scanner attack payload and evidence with a 1-click "Copy evidence"
     button.
   - Clear remediation steps and external OWASP cheat sheet references.

E. Security Analysis Assistant:
   - Replaced static strings with dynamic active-scan analysis.
   - "Summarize active scan": outputs an instant policy compliance briefing.
   - "Explain top finding": details business impact, technical vectors, and
     exploitability.
   - "Remediation guidance": outputs an actionable checklist for developers.

F. Scans & Releases Audit Trail:
   - Scans Page: History of all scan executions with 5-severity breakdown,
     active scan badge, and a "Set as Active" context button.
   - Releases Page: Historical record of gate determinations
     (v1.0.0 PASS, v1.1.0 REVIEW, v1.2.0 BLOCK) using precise "Release gate
     decision" terminology.
